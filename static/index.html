Six rules.
One defense layer.

Requirements mapped to prototype behavior and future engineering work.

RULE 01

⚡ Speed target

Measure local processing time. Target under two seconds for lightweight checks; external APIs may add latency.

METRIC: p50 / p95 latency
RULE 02

◈ New techniques

Combine rules with a classifier and evaluate against phishing samples excluded from training.

METRIC: recall on held-out samples
RULE 03

◎ Fewer false positives

Test against legitimate mail, tune thresholds, and include an uncertain verdict rather than overclaiming.

METRIC: false-positive rate
RULE 04

⌁ URL inspection

Detect encoded URLs, IP hosts, shorteners and suspicious structures. Safe redirect resolution needs an isolated service.

METRIC: URL test coverage
RULE 05

▣ Privacy first

Process in memory, avoid raw-content logs and do not send email content to third parties without clear consent.

METRIC: retention and log audit
RULE 06

⌕ Explainable results

Return findings with severity, plain-language explanations and actionable recommendations.

METRIC: evidence shown per verdict

Privacy by design.
Not an afterthought.

Current prototype behavior and production safeguards.

Current prototype

  • Email and URL data is processed in the API request and is not intentionally written to a database.
  • The application does not automatically open submitted URLs.
  • Do not expose this development server publicly as-is.
  • Production deployment should disable request-body logging, set strict request limits, add authentication/rate limiting, and isolate any URL fetch service.
  • Third-party threat intelligence may receive the queried URL; review each provider's privacy terms before enabling it.
